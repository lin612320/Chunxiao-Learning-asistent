## 一、缺陷 ①：课程选择器不跟随新建课程

### 1.1 现象

在「课程列表」页新建一门课，跳转到课程详情后：
**左上角侧栏的课程选择器里没有这门新课**，顶栏的「当前课程」胶囊也不出现。
只有整页刷新（F5）之后才会出现。

### 1.2 根因：`useCourses` 是"每调用一次就复制一份"的普通 hook

`src/hooks/useCourses.ts` 原来是一个**内部持 `useState` 的普通 hook**。于是**每一处调用**
都会拿到自己独立的一份课程数组，各自在 mount 时拉一次 `courses_list`：

| 调用方 | 用途 |
| --- | --- |
| `components/Sidebar.tsx` | 课程选择器（**用户看到的那个**） |
| `components/Topbar.tsx` | 「当前课程」胶囊 |
| `views/Courses.tsx` | 课程列表页（**发起写入的那一份**） |
| `views/Course.tsx` | 课程详情 |
| `views/Notes.tsx` | 笔记页的课程筛选 |
| `views/Questions.tsx` | 题库页的课程选择 |
| `views/Assistant.tsx` | 对话页的课程选择 |
| `hooks/useChat.ts` / `hooks/useProfile.ts` | 各自内部的课程依赖 |

**共 10 份副本。** 在课程列表页点「创建课程」时，只有 **`Courses.tsx` 自己那一份**会
`refresh()`；而 `Sidebar` 与 `Topbar` 是**常驻组件**（`components/Layout.tsx` 在路由切换时
不重挂载它们），它们的副本**到下次整页刷新前永远不会更新** —— 这就是用户看到的现象。

### 1.3 为什么这跟 R9 是**同一类错误**（第二次犯）

R9 修的是「同一个课程上下文被四个页面各写一遍，只有两个读 URL」（见 `docs/20` §2），
当时的结论是：

> **把"唯一事实来源"写进契约 ≠ 它真的唯一。**

R6 把 `?course=N` 定为唯一事实来源，R9 又让题库/画像去读它 —— 但**课程列表本身**
始终是 10 份副本。R9 的教训只修了"读 URL"这一半，**没有修"数据来源"那一半**。
本轮把这一半补上。

### 1.4 修法：模块级单例 + `useSyncExternalStore`

`useCourses` 内部改成**模块级的单一存储**（`courses` / `loading` / `error` 三个字段 +
一个 `Set<() => void>` 订阅表），用 React 18 的 `useSyncExternalStore` 订阅：

- **写入即广播**：`create` / `archive` / `remove` 改完存储后通知**所有**订阅方，
  于是侧栏选择器与顶栏胶囊**同一帧内**就更新；
- **`getSnapshot` 必须引用稳定**：只维护一个 snapshot 对象、仅在真正变化时替换
  （每次 render 返回新对象会被判定"变了"→ 无限重渲染）；
- **顺带把启动 IPC 从 10 次降到 1 次**（`inflight` 并发去重）。

`useCourses` 的对外形状（`courses / loading / error / setError / refresh / create /
archive / remove / findById`）**一字未改**，所以 9 个调用方一个都没动。

### 1.5 两个单例化之后才会出现的坑（都已处理）

1. **瞬时失败不能抹掉全应用的列表**：`callRust` 失败时返回 `null`（它吞错误，见 `lib/tauri.ts`）。
   原来每组件各存一份时，一次失败只影响自己；单例之后，若把 `null` 当成空数组，
   **一次瞬时 IPC 失败就会把整个应用的课程列表清空**。
   → 改成"**取到数组才替换**"，否则保留上一次的结果。
2. **在途的旧读取不能盖掉刚写完的新数据**：`create()` 之后要 `await refresh(true)`；
   若复用"写入前就已发出"的那次在途请求，就还是读不到新课（正是本节要修的那个坑）。
   → `refreshCourses(force)` + 请求序号 `seq`：**迟到的旧请求直接丢弃**（最新一次说了算）。

### 1.6 第二层：新建的课要**立刻成为当前课程**

光有共享存储还不够：`Courses.tsx` 原来只 `nav('/course/' + id)` —— **不带 `?course=`、
也不记 last-course**，所以侧栏选择器仍停在「全部课程」或上一门课，顶栏胶囊也不出现。

→ 改成与侧栏切换课程**同一套口径**（不另造状态）：

```ts
rememberLastCourseId(id);
nav(`/course/${id}?${COURSE_PARAM}=${id}`);
```

### 1.7 负例验证（**这个断言真的会红**）

只把 `src/hooks/useCourses.ts` 回退到 `HEAD`（即缺陷版），重跑同一条冒烟：

```
[FAIL] 侧栏课程选择器在新建课程后**无需刷新**就出现新课
       — {"before":["全部课程","数据结构与算法",…],"after":["全部课程","数据结构与算法",…]}
[FAIL] 新建的课立刻成为当前课程（选择器选中它） — selected=全部课程
[FAIL] 顶栏「当前课程」胶囊同步出现新课名 — chip=
```

`before` 与 `after` **逐字相同**、`chip` 为空 —— 与用户描述的现象完全一致。
装回修复版后这三条转绿。

### 2.3 为什么编辑区是 `<textarea>` 而不是 `contentEditable`

- `contentEditable` 在**中文输入法**下的 `compositionstart/update/end` 与选区极易错乱，
  而且**撤销栈**要自己实现；
- `textarea` 的输入法支持与原生撤销/重做（Ctrl+Z / Ctrl+Y）是白拿的；
- 代价是"所见即所得"变成"左写右看" —— 这与 Typora **之外**的多数笔记软件一致。

## 三、公式：为什么是 KaTeX，以及它撞了哪条旧约定

### 3.1 ⚠ 依赖登记（**这一条必须留在文档里**）

引入 `katex@0.16.11` **打破了本项目的一条既有硬约定** —— `components/Icon.tsx` 的注释里
白纸黑字写着：

> 「项目硬约定『不新增第三方依赖』，所以图标必须自己画」

`lib/markdown.tsx` 也一直以"**零依赖**手写渲染器"自居。本轮按用户明确选择引入了第一个
第三方前端依赖，**如实登记在此**，并把代价量化：

| 项 | 实测 |
| --- | --- |
| 主包 JS | 392 KB → **407 KB**（KaTeX 已单独拆块） |
| KaTeX 块 | **260 KB**（gzip 77 KB） |
| CSS | 86 KB → **118 KB**（gzip 24 KB） |
| 字体 | **60 个文件 ≈ 1.0 MB**（woff2/woff/ttf 各 20） |
| 依赖树 | `+2 packages`（`katex` 与其 CLI 依赖 `commander`） |

**构建产物里的字体是必须的**：KaTeX 的公式字形全靠这套字体，缺一个字符就会显示成方块。
所以这 1 MB **不能省**，只能如实记在账上（安装包本来就 82 MB，占比很小）。

**为何单独拆块**：并进主包会让主包 392 → 669 KB、**跨过 vite 的 500 KB 阈值**，
每次构建都打一条 chunk 过大的警告 —— 本项目历来把"构建 0 warning"当口径，
不该因为引入公式能力就默认接受一条长期警告。拆块后主包 407 KB、**0 warning**
（而且公式只在正文真的出现 `$…$` 时才需要解析）。

### 3.2 安全红线怎么守住的

`lib/markdown.tsx` 的头号红线是：**禁止 `dangerouslySetInnerHTML`、禁止拼接 HTML 字符串**。
而 KaTeX 最常用的 API 恰恰是 `renderToString()` —— 它返回 HTML 字符串，只能用 innerHTML 塞进页面，
**直接违反红线**。所以这里用的是命令式 API：

```ts
katex.render(tex, domElement, { displayMode, throwOnError: false })
```

它直接在真实 DOM 上建节点，全程不经过任何 HTML 字符串。已在两个文件上 grep 确认
`dangerouslySetInnerHTML` **零出现**。

KaTeX 的 `npm` 包里**没有 `.d.ts`**，而本轮约束是"不再装别的东西"，所以 `lib/math.tsx`
用命名空间导入 + **就地收窄**（只声明 `render` 一个成员），并用 `@ts-expect-error` 精确抑制
TS7016 —— 将来若补上类型声明，这行会立刻报"未使用的 expect-error"，**逼着维护者把它删掉**，
而不是留一句永久静默的 `@ts-ignore`。

### 3.3 语法规则（逐条，可复核）

| 项 | 规则 |
| --- | --- |
| 行内公式 | `\$(?!\s)([^$\n]+?)\$(?!\d)` —— 开定界符后**不能是空白**，闭定界符后**不能是数字**（后者专为挡 `$5 and $10` 这种钱数） |
| 块级公式 | 整行 `$$…$$`，或 `$$` 单独成行到下一个 `$$` 之间的**多行**内容 |
| 分词顺序 | **公式先切、其余再走强调规则**：否则 `$a_1 * b_2$` 里的 `_`/`*` 会先被斜体规则抢走。分开处理后 `*$a$*` 能正确渲染成"斜体里套公式" |
| 代码围栏内 | `` ``` `` 里的 `$` **一律按字面**（公式不在代码块里识别） |
| 错误公式 | `throwOnError: false` → KaTeX 用 `.katex-error` **红色回显原始 TeX**，不抛异常、不白屏（本项目"宁可显示原文也不崩"的口径） |

### 3.4 未处理的边界（如实登记）

行内公式**不把 `\$` 当转义**。`\$5 and \$10` 这种写法**不会**被误判（两个 `$` 都过不了
定界规则），但**转义美元与真公式混排**时仍会出错：

> `\$5 和 $x$` → 中间那段 `$5 和 $` 会被当成一个行内公式。

彻底修法是给两个定界符加 `(?<!\\)` 负向后顾，但那会让"公式体以反斜杠结尾"的写法失效；
而公式体本来就**不允许含 `$`**（`[^$\n]`），所以真正的收益很窄。本轮**不做**，
登记在此而不是假装没有。

## 四、顺手补上的一处真缺口：渲染器**根本不支持图片**

### 4.1 缺口是怎么被发现的

新加的冒烟断言「插入的图片在预览里真的渲染出来」**第一次跑就是红的**：

```
[FAIL] 插入的图片在预览里真的渲染出来 — {"ok":true,"inText":true,"rendered":0}
```

`inText: true` 说明图片**确实写进了 `content_md`**，但预览里 `<img>` 数量是 **0**。
查下来是**两层叠加**：

1. `lib/markdown.tsx` 的渲染器**从来没有图片规则** —— 只有 `[label](href)` 链接，
   `![alt](src)` 会被拆成"一个 `!` + 一个链接"；
2. 而 `safeHref()` 是**链接**白名单，只放行 `http:` / `https:` / `mailto:` ——
   它**刻意**拒掉 `data:`（挡 `data:text/html` 这类注入面），所以粘贴的 dataURL 图片
   即使被识别也只会**降级为纯文本**。

也就是说：**"笔记支持粘贴图片"这个需求，光在前端插入 Markdown 是不成立的** ——
用户会得到一段**看起来像图片、实际什么都不显示**的源码。

### 4.2 修法：给图片**单独开一个更窄**的白名单

```ts
const IMG_DATA_SRC_RE = /^data:image\/(?:png|jpeg|jpg|webp|gif);base64,[A-Za-z0-9+/]+=*$/i;
```

- **只放行图片型 dataURL**，且**刻意排除 `image/svg+xml`** —— SVG 是可执行文档类型，
  将来只要有人把同一段地址放进非 `<img>` 的上下文（`<object>` / 直接导航），它就是脚本注入面；
  而 `lib/images.ts` 的 canvas 管线**只产得出 png/jpeg**，排除它**挡不住任何真实用法**；
- 仍然放行 `http(s):` 的普通图片地址；其余一律返回 `null` → **整段降级为纯文本**（与链接同口径）；
- **偏移尺子保持一致**：`<img>` 在 DOM 里不产生任何文本，所以 `plainInline()` 也让图片
  贡献 **0 个字符** —— 这条不变量在有图的块上**照样成立**（比公式那一段干净）。

> 📌 **本轮最该记住的一条**：这个缺口**不是靠读代码发现的，是靠"让断言真跑"发现的**。
> 与 `docs/22` §五.3（悬浮球抽屉叠字：8 层验证没一层会红）是同一个道理 ——
> 覆盖到"我以为该看的地方"不等于覆盖到用户会碰到的地方。
> 本轮的做法同样是：**补上那一层，并确认它真的会红**。

## 五、已知局限（如实登记）：含**行内公式**的块，批注偏移对不上

批注锚点是"**块内纯文本字符偏移**"，靠 `[data-block]` 元素的 `textContent` 与
`blockPlainTexts()` 用**同一把尺子**来保证（`docs/07` §三）。

公式破坏了这条不变量：KaTeX 画出来的 DOM 里是**真字符**（MathML 文本 + 拼出来的字形），
所以"含公式的块"其 `textContent` 会**长于** `blockPlainTexts()`。

- **本次选择"尺子优先"**：公式对纯文本游标的贡献 = 它在原文里的那段字符串
  （行内 `$E=mc^2$` 算 8 个字符），保证偏移在两侧**逐位对齐**；
- **影响面**：只有**恰好含行内公式**的块，批注高亮边界可能整体偏移几个字符；
- **不做 Shadow DOM 就无法两全**（要么丢公式的可见文本、要么破坏偏移尺子）；
- **处置（不是"以后注意"）**：
  1. 渲染器导出 `hasInlineMath(md)` / `blockHasInlineMath(md)`，让调用方能**提前知道**；
  2. `views/Notes.tsx` 的选区处理**拒绝在含行内公式的块上新建批注**，并如实说明原因 ——
     与其存一条**位置注定错**的批注（用户看到的高亮会偏），不如说一句"这一段暂不支持"；
